# Architecture — Unified Job Pipeline

The shape of the system as built. Updated at the close of every phase, so a new session can read this instead of rebuilding context from the conversation.

Decisions and their reasons live in [decision-log.md](features/_complete/unified-pipeline/decision-log.md). This file describes what exists; that one describes why.

## Status

Phases 1 through 12 complete. One command runs the whole pipeline, and every deterministic step runs end to end. Two further commands run scoring, which is the one step an agent does the judging for. Three more stand outside a run entirely: one finds a job by its employer, one changes a job's status, and one serves a read-only dashboard over everything the pipeline has decided. Each step reads its own work out of the database and ends by writing back, so no step depends on another holding a list in memory.

**Before anything else, the database is checked against the code.** One row is read from each model, and a run that cannot read them all stops there, names the tables and the command that rebuilds them, and exits non-zero. This costs nothing and guards the failure that destroyed a run silently: a column added to the schema and never pushed to the live database, which made every trace write of that run fail and left no record it had happened.

**The collection step.** Seven collectors produce a job list, every job that survives is normalized, each is attached to the company it belongs to, duplicates are merged to one entry per real posting, and the whole list is written: a job not on file is created carrying the id it was given at collection, one already on file takes the better of the two copies field by field, and a row dedupe marked is deleted. `npm run job-search` therefore leaves rows behind rather than a list in memory.

**The resolution step.** It reads every job still waiting to be followed — one whose status is `backlog` and whose resolution flag is false, whenever it was collected — launches one visible browser, and follows each listing link towards the employer's own posting. A job's resolution that arrives writes the address it arrived at. A job's resolution that reaches a site on the blocked list marks the job for removal, unless the user entered it by hand, in which case it is parked instead: no collector would ever find it again. The resolved list then goes through the same dedupe and save the collection step ends with, at two trace points of its own. Four of the seven collectors host their own postings and mark their jobs resolved as they collect them, so nothing resolves those.

**A failure that describes the moment keeps its job.** A source that refused us and a page the browser could not load both say nothing about whether the posting is any good, so those two leave the job's status untouched and the next run tries again. Every other failure parks the job as `unresolvable` for the user to repair. Before this split, a single bad afternoon at one source took 100 of 334 jobs out of the pipeline for good.

**Resolution runs two lanes.** The queue is dealt round-robin by host first, so no source receives our whole queue in one burst. The fast lane then works it three jobs at a time. A host that refuses us sends its remaining jobs to a slow lane, along with the job whose own attempt proved it, and that lane runs after the fast one with a pause between its jobs. Nothing names a host: which hosts reach the slow lane is decided entirely by what they did during the run, and the set starts empty every time. A refusal is read from any page the browser navigated to, wherever in the redirect chain it sat — a source that refuses and then redirects away from its own refusal would otherwise never be slowed down. The two lanes cut the cost of a block; they do not prevent one, because the fast lane has no pacing of its own.

**The parsing step.** It reads every job already resolved but not yet parsed, and reads each one's posting with the parser owning its resolved link's domain. Four parsers exist — Greenhouse, Lever, Ashby and Dribbble — and a job whose domain none of them owns is set aside as `unparseable` rather than read from a stale aggregator copy. Whatever fields a parse finds are folded onto the entry, and the list then goes through normalization, association, dedupe and save again, at four trace points of its own. No parser opens a browser: three read a public JSON API and Dribbble reads a server-rendered page with a plain fetch.

**The backlog cleanup step.** It opens the run, before any collector, so the backlog being added to has already been swept. Every job in the backlog is read, one past the expiry threshold takes the status `expired`, and the rest are untouched. The list is then saved.

**The same sweep clears stale judgements about employers.** A second half reads every company that carries a score. One scored longer ago than the score expiry loses all four of its scores and is researched again. A category the agent guessed at, because nothing public existed, is emptied sooner than one it researched — a guess wearing the same clothes as a judgement is what the guessed list exists to tell apart. The two halves are two functions in one handler, each taking its own kind of list, and each writes its rows under the same step name. Scoring runs this sweep as it opens, so a judgement that went stale overnight is gone before anything asks who needs a score.

**The promotion step.** An employer that lists a role again gives it a fresh posting date, which pulls the job's age back inside the threshold. Those jobs return to the backlog marked as not yet judged, so classification reaches its own conclusion rather than keeping the one that expired them. It runs late rather than early, because an expired job only gains that fresh date once collection has found the new listing and dedupe has merged it in — run first, it would find nothing.

**The classification step.** It reads every backlog job that is resolved, parsed and not yet judged, and asks three questions of each. A job carrying two posting dates further apart than the repost gap is flagged as a repost. A job past the expiry threshold takes `expired` and stops there, so no paced map request is spent on a job the user cannot apply to. Everything else is matched on location: every place the job names is paired with every work mode it offers, and any one pair passing is enough.

**How close is close enough depends on the work mode.** Hybrid and in-person measure travel distance only, so an office the user cannot reach is never accepted just for sitting inside a region they live in. Remote and unknown accept either distance or containment, so a role open across a whole country is not turned down for the country being large. Whether the user lives inside a place is decided by that place's own outline on a map, never by comparing names — a name comparison put a job in Austin, Arkansas into the backlog. Where several pairs pass, the place whose centre is nearest is the one recorded.

**A place we could not read is not proof a job is far away.** A job whose every place failed to resolve keeps its status, is not marked judged, and waits for a later run. A refused map request is recorded the same way, so one refusal costs one job rather than the rest of the list.

**A place is looked up once and reused.** Across the real database, 3,975 lookups resolve to 789 distinct places, so a run only pays for places it has never seen. A place that resolved to nothing is not stored, which is what leaves it to be tried again once the splitter improves. The map service allows one lookup a second, and the tool holds its own timer rather than trusting every caller to wait.

**The scoring step, and why it is two commands.** An agent does this judging, and no single command can pause while it thinks. So scoring is a second orchestrator with two starting points rather than a handler in the run. `npm run score:gather` sweeps the backlog, asks the database for every backlog job that is resolved, parsed, judged and still unscored, and for every company still missing a score, and writes them out as one JSON file. An agent reads that file, scores each job against the alignment rubric, and researches each employer against the company rubric. `npm run score:save` reads its answers back, writes them through the job service and the company service, and records what became of every entry. A job's score is one number and one sentence; a company's is four numbers and four sentences, one per category.

**Save runs once per batch rather than once per run.** An agent produces its answers a handful at a time, and a run that stops halfway still keeps the research it already paid for. The last batch is the one that asks for a summary, because reprinting a growing summary after each batch is noise.

**A score answer carries only an id.** A trace row about a job has to name the collector that produced it, so the save half reads the "who still needs a score" list first and builds an id-to-collector map from it. Nothing trusts the agent to hand a collector back.

**The company promotion step.** It closes each save batch. A company whose four scores average above the promotion threshold has its board row filled in with the collector that will poll it, and from the next run its postings arrive first-hand instead of by way of an aggregator. The average rather than each category on its own: the company rubric awards a 3 where nothing public was found, so a per-category test would block a strong employer forever on one unknown. A company missing any score has no average to test and is skipped before the threshold is reached. Promotion changes nothing about the company itself — the board row already existed, written when the posting was parsed, and promotion only adds the collector. Three boards can be polled, so a company on any other system is skipped as having no pollable board.

**The status change, which no run ever starts.** Everything above happens inside a job search. `npm run change-status` runs because the user says a job moved. It reads a submission off disk — a list of job ids and the status each takes — refuses the whole list if any status is not one of the twelve, writes every status, and prints one line per job. A submission is refused whole rather than applied in part because half a batch landing is worse than none: the user would then have to work out which half.

**Three statuses file a legal record.** `app. sent`, `screening` and `interview` are what the Texas Workforce Commission counts as a job search activity, and each writes a work log entry carrying the employer name, the job title and the Commission's own wording for that activity. The trigger is the arriving status, never which write path the job service took — hanging it on the status-only path would have skipped the first entry for every job and caught only later moves. The entry copies the employer name and the title onto itself and holds its job's id as a plain column with no relation, so a filing survives the job or the employer behind it going away. Nothing revises an entry, so there is no update and no last-changed column.

**A job with no employer name stops and asks.** A filing naming a blank employer is worthless, so a job linked to no employer, or to one holding no name, is left unchanged and reported as needing a name. The user supplies it, the run matches it against employers already on file, creates one only where nothing matched, and links the job to the result. The nameless employer is left exactly as it stands, and so are its other jobs.

**Then the employer's contact details are searched for.** Every status and every work log entry in a batch is written before the first search starts, so a command cut short loses searches and never loses a filing. A paid search service is asked one query per employer — the name, plus the place the job's location matched where it has one — and an address, a phone number and a website are read only out of a result whose title names that employer. An employer already filled in is never asked about again, and an employer named twice in one submission is looked up once. A search that filled nothing in leaves the employer open to a later search, so a failure costs one run rather than the employer forever. Details the search is unsure about are flagged, so the user checks them before filing rather than after.

**Finding the job the user means.** Every job command needs an id and the user has none — a job is named by a pasted link, or by who is hiring and roughly what the role is. `npm run find-jobs` takes a link, part of an employer's name, or both, and optionally a list of statuses to stay within. A link is tried first: it is cleaned into a match key the same way saved links are, and matched against both saved links of every job. When the link matches nothing, or is not a web address, and an employer was given, the employer's jobs answer instead. The role is never searched: the agent reads the employer's jobs and picks the one the user's words describe. The command prints one JSON object naming which search found the jobs (`found_by`), any problem with the link (`link_problem`: `no_match` or `not_a_link`), and the jobs, newest posting first, each with its id, title, employer, status, posting date, both links and location. An empty job list is an ordinary answer. The `change-status` skill runs it first and narrows it by the status being set: moving a job to `app. sent` searches the backlog alone, and moving one to `rejected` or a later active status searches the active jobs alone. A search across every status would ask the user to choose between a backlog job and two closed months ago, when the status being set already says which was meant.

**One command, and what it reports.** `npm run job-search` builds the connection, the services, the run id and the date, hands the orchestrator the real browser, and prints what came back. A handler that throws stops the run where it happened rather than escaping: the report names the spot and the reason, lists the handlers that finished with their counts, and the command exits non-zero. Every step ends in a database write, so a run that stopped keeps whatever the finished steps saved.

**The summary.** The command prints a summary rather than a job list — several steps each printing every job buries the run in its own output. It is read back from the run's trace rows rather than taken from what the orchestrator returned, because the return value carries list lengths alone while the per-collector and per-reason numbers exist only in the rows. Every future phase adds its trace rows and its own block in that summary. Scoring's two blocks are printed by `npm run score:save` instead, because the pipeline has already finished by the time they exist, and only on the last batch, since reprinting a growing summary after each batch is noise.

Save is the one part that guardrails the user's own work. A job in a status meaning the user has applied is frozen except for its status, and a delete against one is refused with the row kept and a warning saying why — one wording for a duplicate, another for a blocked site.

Dedupe runs twice over: the list against itself, then each survivor against the rows the table already holds. Two runs of `npm run job-search` therefore leave one row per posting rather than two — measured on 2026-09-10, a second run over the same 21 collected jobs updated 20 rows and created none.

Tracing is live across every built step. A job search mints a run id, every job is given an id as it enters the collection loop, and each step writes its own events to the `Trace` table. Scoring's two commands write under the same run id the pipeline used, so both halves of one search land in the same counting bucket. A row names a job or a company, never both: a job row carries the collector that produced it, and a company row carries neither a job nor a collector, because a judgement about an employer has no collector behind it. "How many jobs did each collector produce", "how many titles normalized, by collector", "how each job reached its company", "what dedupe merged away and what it became", and "how many rows each collector had created against updated", and "which rule accepted each resolved job" are all answerable from the database alone. So is the one question that spans the whole pipeline: reading each job's most recent row answers what the pipeline dropped and where.

**The dashboard, which reads and never writes.** `npm run serve` answers one address with the whole page: the backlog, the jobs applied to, the jobs ruled out, and the work log, with a small script showing one list at a time. It reads through the services that own each table rather than the database itself, and writes nothing at all — no status change, no trace row, no record that a page was ever opened. A page that filed a record of being read would put every glance at the backlog into the same counting buckets a run is measured by.

**It refuses to listen against a database that does not match the code.** The same schema check every command runs happens inside the server rather than before it, because a dashboard has to refuse the port rather than merely exit: a blank browser tab says nothing about what went wrong, and an empty page reads exactly like an empty backlog. A mismatch answers with a page naming the tables instead.

**A job's total is worked out as the page is built, never read from a column.** Four of the five ratings behind it sit on the employer, so an employer rescored after its jobs were saved moves all of them at once. That is also why the page's two job reads hand back the job and its employer side by side. The total leaves the applied-to and ruled-out lists entirely — once the user has applied, the total decides nothing, while the five categories still say what kind of job and employer it was.

**The reasoning tooltip carries the job's own reasoning alone.** The employer's four written judgements were tried there first and judged by eye on 2026-09-17: five blocks came to 2,848 characters, which a browser tooltip cuts off. The four are saved and shown nowhere until a panel exists that can hold them, which is a backlog item rather than this phase's work.

**Every file in `lib/` sits in a folder named for the kind of thing it is**, and `lib/` itself holds no file of its own. `lib/collectors/` and `lib/parsers/` hold the only differentiated code. `lib/handlers/` holds one handler per file — backlog cleanup, collection, normalization, association, dedupe, resolution, parsing, save, promotion, classification, company promotion, status change and employer search — and `lib/orchestrators/` the three things that run them, the job search, scoring and the status change. `lib/resolvers/` holds the code that follows a job link toward its source posting. `lib/tools/` holds the browser, the page fetcher, the map service, the paid employer search and the web server, the only parts that reach outside the app. `lib/views/` holds the code that turns data into a screen, and is the only folder allowed to write HTML. `lib/services/` holds one file per table or row, `lib/db/` the connection and the schema check, `lib/types/` the shapes shared across folders, and `lib/utils/` the plain functions that take values and return values. The map is written down in `.claude/rules/naming.md`, so where a file sits answers what kind of file it is. `legacy/` is gone, deleted at the switch over.

## Principles

The principles that govern where new behaviour goes now live in [`.claude/rules/part-ownership.md`](../.claude/rules/part-ownership.md), together with the table saying what each part owns and never does. They are a rule rather than a description, because they constrain work that has not happened yet.

## Vocabulary

- **Job List** — the list of jobs held in memory during a job search, passed between steps and eventually saved.
- **Job abandoned** — a job whose path through the pipeline ended, whatever step ended it and whether or not it ever held a database row. What became of the row is recorded separately. A job parked at a status the user can repair has paused rather than ended, so it never takes `job_abandoned`.
- **Step** — one stretch of the pipeline that reads its own work out of the database, acts on it, and writes back. Collection is the first, resolution the second, parsing the third.
- **Lane** — one pass of the resolution step over a set of jobs, at its own pace. The fast lane takes every job; the slow lane takes the jobs of hosts that refused the fast one.
- **Owned domain** — the domain a company registered, one label above the public suffix. What a parser is matched on, so three Greenhouse hosts collapse to one `greenhouse.io`.
- **Run** — one job search. Every trace entry belongs to one.
- **Active job** — a job whose status says the user has applied and has not been rejected. Frozen except for its status, and never deleted by a merge.
- **Hard Match** — two jobs that are identical: an identity match whose dates agree.
- **Repost Match** — two jobs that are the same role posted again: an identity match whose dates differ.
- **Identity** — a matching original URL, a matching resolved URL, or company plus title with the two sides' dates inside 30 days. What makes two records one job, before dates decide which kind of match it is.
- **Place** — one location text and what the map service answered for it: coordinates, a type, a display name and an outline where it has one. The text is the place's whole identity, so two jobs naming a place the same way share one row.
- **Pair** — one of a job's places set against one of its work modes. A job passes the location test if any pair passes; a job carrying no mode is paired with an unknown one.
- **Repost** — a job whose two posting dates sit further apart than the repost gap setting, which reads as the employer listing the role again rather than as two collectors disagreeing by hours about one posting.
- **Board row** — one record saying a company posts on a hiring system: the board's slug, the company, the parser that read the posting the slug came off, and the collector that polls it where one does. A row with no collector is a board we know about; a row with one is a board we poll.
- **Alignment score** — how well one job fits the user, one number and one sentence, judged by an agent against the alignment rubric. Empty is what says the job still needs scoring.
- **Company score** — what an agent researched about an employer, four numbers and four sentences: employee satisfaction, customer satisfaction, work-life balance and political alignment. One date covers all four.
- **Guessed category** — a category the agent found nothing public for. The rubric awards a 3 either way, so the guessed list is the only thing telling a placeholder from a judgement, and a guess goes stale sooner.
- **Promotion** — two different things, spelled apart on purpose. A job's promotion returns a reposted job to the backlog. A company's promotion puts an employer's board on a polling list.
- **Work log entry** — one recorded job search activity for the Texas Workforce Commission. Written when a job takes `app. sent`, `screening` or `interview`. A legal filing that cannot be regenerated once the week it belongs to has passed.
- **Activity wording** — the Commission's own phrase for one kind of activity. A fixed value rather than a label anyone may reword, because a filing is rejected on wording the form does not recognize.
- **Contact details** — an employer's address, phone number and website, which a Commission filing asks for. Filled in by a paid internet search, never by the pipeline.
- **Doubt** — a note that one contact detail is worth checking before filing: an address that does not read as a United States address, a missing address, a missing phone number.
- **Submission** — one list of status changes handed to `npm run change-status` as a file. Refused whole where any status is not one of the twelve.
- **Ruled-out job** — a job the pipeline or the user has taken out of the running: expired, too far, won't apply, unresolvable, unparseable or rejected. The dashboard's third list.
- **View** — code that takes data already read and returns the HTML for a screen. The only kind of file allowed to write markup, which is the whole of what separates it from a util.
- **Benefit week** — the Sunday-to-Saturday span the Texas Workforce Commission files a work log for. What the work log page groups by, counted in local days rather than a fixed number of hours.

## Run Shape

A skill triggers three commands in turn. The first runs deterministically to completion, leaving a backlog that is fully collected, resolved, parsed, and classified — everything in it new enough and close enough. The second and third are scoring, split in two so an agent can think between them. The dashboard is served afterwards.

```
npm run job-search
  backlog cleanup → save
    → collect → normalize → associate → dedupe → save
    → resolve → dedupe → save
    → parse → normalize → associate → dedupe → save
    → promotion → save
    → classification → save

npm run score:gather
  backlog cleanup, jobs → save
    → backlog cleanup, companies → save
    → gather everything still needing a score, and write it out

  ( an agent scores each job and researches each employer )

npm run score:save  — once per batch of the agent's answers
  write the scores → company promotion
```

These nodes are the step vocabulary a trace event records, in this order. Tracing is not a step of its own: it is the record of a job's passage through these. All three commands write under one run id, so a search counts as one run however many commands it took.

A status change stands outside all of it. No run starts it, it writes no trace rows, and it has a shape of its own.

```
npm run find-jobs -- [--url "..."] [--company "..."] [--statuses "..."]
  search the link → fall back to the employer → print one JSON answer, newest first

  ( the user, or the change-status skill, reads off the job ids )

npm run change-status -- --in FILE
  write every status → write each work log entry the status calls for
    → search for each employer's contact details
```

The searches run last on purpose. A work log entry is a legal filing that cannot be regenerated once its week has passed, and a search is the slow part, so a command cut short loses searches and never loses a filing.

The dashboard stands outside it all as well, and further out than a status change does: it mints no run id, writes no trace rows, and changes nothing in the database at all.

```
npm run serve
  check the database matches the code — refuse the port if it does not
    → read the backlog, the active jobs, the ruled-out jobs and the work log
      → build one page holding all four
```

## Parts

Written as each phase lands. Each entry records what the part does, what it refuses to do, and who calls it.

Three kinds, and the difference is the database. A **service** is handed the database connection and hands back a small object holding a few functions. A **handler** takes the job list, acts on every entry, and returns it with its warnings, under the contract in [`.claude/rules/handler-contract.md`](../.claude/rules/handler-contract.md). A **util** takes values and returns values, reaching no database at all.

A **view** is a fourth kind, added by phase 12. It takes data already read and returns the HTML for a screen. What separates it from a util is only that it writes markup: a util that returned a tag would put HTML in a folder nobody would look in for it, so `lib/views/` is the one place markup is built.

An **orchestrator** sits above all three: it reads the work out of the database, calls each handler in turn, and writes back. Three exist. The job-search orchestrator runs the whole deterministic pipeline in one pass. The scoring orchestrator has two starting points instead of one, because an agent does its judging and a command cannot pause while it thinks. The status-change orchestrator runs outside any job search, because the user rather than a run is what starts it.

| **Company service** — `lib/services/company-service.ts` | Service | Owns every read and write of `Company`: find by slug, find by match key, find by id, create, fill an empty name, list every company still needing a score, list every company that carries one, mark a company as being searched, save the contact details a search found, and write a score block either from an agent's answer or from a record a handler already worked out. A write covers only the categories it was handed, so a company already holding three keeps them. It also holds the list of the four categories, so a fifth would be added in one place, and the list of the employer's own columns with the step that reads a stored row back — both shared with the job service, whose dashboard reads have to build an employer too. Collectors are the differentiated code and are none of the three kinds above. Seven exist: `adzuna`, `jsearch`, `greenhouse`, `lever`, `ashby`, `dribbble`, `uiuxjobsboard`. They share helpers rather than a base class — `fetch-utils`, `fetch-page`, `paginate`, `ats-boards`, `match-categories`, `fixture`. `ats-boards` asks the ATS slug service for the boards one collector polls, by that collector's own name, and an empty list is a real answer rather than a broken database: emptying a collector's list is how it gets switched off, so the emptiness is warned about rather than hidden. `fixture` still writes a saved page copy on demand, but neither page-reading collector calls it any more — a real search rewriting its own test input dirtied the working tree every run, and a command that refreshes one deliberately is on the backlog.

Parsers are the other differentiated code, and are differentiated for the same reason: each reads one source and interprets what it finds. Four exist: `greenhouse`, `lever`, `ashby`, `dribbble`. Three read a public JSON API and open no browser; Dribbble reads a server-rendered page with a plain fetch, and opens none either. No parser drives Playwright — the legacy Ashby parser did, scraping a data blob out of a rendered React page, and this one reads the same endpoint the Ashby collector reads instead.

## Data Model

Grown phase by phase. The database holds nothing worth keeping until the switch over, so it is dropped and recreated freely. It is a separate file from the old pipeline's, reached through `PIPELINE_DATABASE_URL`, and its client generates to `generated/pipeline`.

| Model | Holds | Written by |
|---|---|---|
| **Job** | One posting. Every field a source published lives under a `raw_` prefix, kept exactly as published; the normalized and classified fields beside them are filled by later phases. `title`, `normalized_mode_list`, `salary_low`, `salary_high` and `salary_period` are the ones normalization fills, and `raw_company_name` is the one field it rewrites in place. `original_url_match_key` and `resolved_url_match_key` hold each link squashed for matching, both indexed and neither unique, because two rows for one posting share a key until the pass that collapses them. `normalized_location_list` holds each collected location cut into single places, and `location_match`, `location_match_place`, `location_match_mode` and `is_repost` hold what classification decided. `location_match` has three states rather than two: empty means no place on the job could be read at all, which is a different answer from too far, and a job sitting empty is left in the backlog for a later run. Three phase gates — `is_resolved`, `is_parsed`, `is_classified` — are how each phase finds its work. `alignment_score` and `alignment_rationale` hold how well the job fits the user and why; empty is what says it still needs scoring, so the column carries no default and a promoted job is emptied. `collector` and `parser` record the winning side of the merge; `collected_at` is written by the orchestrator when this pipeline first sees the posting and is never overwritten. | The job service, through the save step |
| **Company** | An employer and what an agent researched about it. `name` is optional, because a company met only as a board slug carries none and nothing invents one; `match_key` holds the name squashed for matching, and both are unique, so the database refuses a duplicate employer whatever the matching code does. Four score columns and four rationale columns hold the judgement — employee satisfaction, customer satisfaction, work-life balance and political alignment — one rationale per category rather than one field holding all four, so re-scoring one category writes one field. `scored_at` is a single date covering all four. `scores_guessed` lists the categories the agent found nothing public for; the rubric awards a 3 either way, so that list is the only thing telling a placeholder from a judgement. Seven more columns hold what a paid internet search found for a Texas Workforce Commission filing: `address`, `phone`, `website`, `enriched_at` saying when a search last filled something in, `enrichment_status` saying what that search did, `enrichment_uncertain` saying whether anything is doubtful, and `enrichment_flags` naming the doubts. Only those seven keep the word `enrichment`; every document and message about them says contact details. Which boards the company posts on live in `AtsSlug` rather than here. | The seed script, company association, backlog cleanup's company sweep, scoring, and the employer search |
| **AtsSlug** | One board row: a slug on a hiring system, the company whose board it is, the parser that read the posting the slug came off, and the collector that polls it where one does. The pair of columns this replaced forced two different facts to travel together — that a company posts on a hiring system, and that we poll its board every run. Company association writes the row as soon as a posting is read, with no collector; promotion fills the collector in, and filling it in is what starts the polling. `slug` is unique, because a job carries a slug without carrying which board it came from, so a slug held by two rows could not be resolved to one company. `collector` is indexed, because each ATS collector asks for the rows carrying its own name. | Company association, and company promotion |
| **Setting** | Single-row configuration: search terms, location, radius, expiry threshold, the three resolution lane settings — fast width, slow width and the slow lane's pause in seconds — the repost gap in days, the four title vocabularies — head nouns, levels, suffixes and removal words — `source_priority_list`, and the three scoring settings: the promotion threshold a company's four scores must average above, how many days a researched score stands, and how many days a guessed one does. The threshold is tested against the average rather than each category, because the company rubric awards a 3 where nothing public was found and a per-category test would block a strong employer forever on one unknown. The pause is stored in seconds because that is the unit a person tuning it against a source that pushed back thinks in; resolution is handed milliseconds. The vocabularies live here as data so the Web UI can offer a screen to edit them without a code change. The priority list is one flat order ranking every parser and collector together, each line prefixed by its kind, so `parser:greenhouse` and `collector:greenhouse` are two separate entries. | The seed script, which fills what is absent and overwrites nothing |
| **Place** | One looked-up location: the text that produced it, its coordinates, its type, its display name, and its outline where the map service gave one. `lookup_text` is the place's whole identity, so two jobs naming a place the same way share one row. A place that resolved to nothing is absent rather than stored empty, which is what leaves that text to be tried again on a later run. | The place service, during classification |
| **WorkLogEntry** | One recorded job search activity for the Texas Workforce Commission: its own id, the job's id, the employer name, the job title, the activity's wording, and when it was created. The employer name and the title are copied onto the row rather than read through to the rows holding them, and `job_id` is a plain column with no relation, so a filing survives the job or the employer changing or going away — the old pipeline made the row depend on a job the pipeline is allowed to delete. No last-changed column, because nothing revises an entry. | The work log service, through the status-change handler |
| **Trace** | One row per event in a job's path through the pipeline, or in an employer's shorter path of its own. `run_id`, `step`, `event`, `reason`, `collector` and `domain` are the columns a query groups by; `detail` holds what is only ever read one row at a time. A row names a job or a company, never both: `job_id` and `company_id` are each optional, and a company row carries no collector, because a judgement about an employer has none behind it. `domain` carries the owned domain a parse failed on, which is what makes a failing platform countable when every employer sits on its own subdomain. Neither `job_id` nor `company_id` carries a foreign key, so a trace outlives what it describes, and the integer primary key orders two events landing in the same millisecond. No scoring row carries the score itself — a score is a counted value, so it lives in a column on the row it describes and a reader joins to it. | The trace service, called during a job search and during scoring's two commands |

The step and reason vocabularies live in the `Trace` model's comment in `prisma/schema.prisma`, in pipeline order. Every step is written today — collection's six usability codes, normalization's ten, association's six, save's one, dedupe's four, resolution's ten, parsing's three, the judging steps' three, and scoring's seven alongside company promotion's four. Company promotion is spelled apart from promotion, which means a reposted job returning to the backlog, because scoring shares the job search's run id and one name would put both in the same counting bucket. Every event about a job carries the `job_` prefix, so a row's subject reads off its event name alone, and a failure event carries its step's own spelling — `parsing_failed` beside `classification_failed` and the rest. A reason string is never shared by two different populations, so a query grouping by reason alone never merges groups with nothing to do with each other — which is why association's dead end is `no_company_name` rather than the `no_company_identity` collection already owns. Two steps may share one where they describe a single population split by where it happened, and `event` is what says which side of the split a row sits on: scoring writes `no_company_name` too, normalization and classification both write `location_unusable`, and every expiry in the pipeline writes `past_expiration_threshold`. Steps do share an event name where the same thing happened to the job, and `step` and `reason` are what tell the populations apart: save reuses collection's `job_abandoned` for a write that threw, dedupe reuses it for every entry it merges away, and resolution reuses it for a collected job whose resolution reached a blocked site. `job_abandoned` says a path ended and claims nothing about whether a row existed; `job_dbrow_deleted` and `job_dbrow_delete_refused` are what say what became of the row. `detail` holds a plain string for most events, the before-and-after pair for a normalization, and a named record for the two events that need several values at once — a merged-away job's row and a refused delete's.

Three commands manage the database, and the switch over changed what each is for. `npm run db:create` rebuilds a database from the schema, and takes its target as an argument: it has no default, and it refuses outright the file `PIPELINE_DATABASE_URL` names in the repo's own `.env`, read from that file rather than from the environment so a shell override cannot make a wipe of the real database look safe. `npm run db:migrate` is the schema-change command from the switch over onward — it copies the file to a dated backup, adopts the committed `prisma/migrations/0_init` baseline where the database has no migration history, then runs Prisma's migration workflow, so a schema change keeps every stored row. `npm run db:seed` fills absent settings, overwrites nothing, and appends every collector and parser registry name missing from the priority list to the bottom of it — a rule at [`.claude/rules/source-registry.md`](../.claude/rules/source-registry.md) requires it to run in the same change that adds, removes or renames a registry entry. It creates no company and no board row: a board is polled because an employer scored well enough to earn it, never because the seed armed it. The reset command is gone, deleted with `legacy/` — it existed because the database held nothing worth keeping, and the switch over ended that.

Two commands stand outside the pipeline and serve the skills. `npm run find-jobs` searches a pasted link first and part of an employer's name second, and answers with one JSON object carrying which search found the jobs, any problem with the link, and each match's identifying fields, its location, and both its links. `npm run fetch-rendered-page` takes `--url` and prints one page's finished HTML after its scripts have run, through the browser-driven fetcher in `lib/tools/rendered-page-fetcher.ts` — named for what it does, so it cannot be confused with `lib/tools/fetch-page.ts` beside it, which reads raw page text and runs no scripts. The resume skill calls both, and the `change-status` skill calls `find-jobs` too.

`npm run job-search` prints its run identifier as its first line, before anything else runs. Scoring files its trace rows under the same identifier, so the two halves of one search land in one counting bucket, and that printed line is the only place a skill can read it from. `npm run score:gather` takes that identifier through `--run-id`, and warns when an identifier it was handed matches no trace rows — a stale or mistyped one would otherwise file this scoring silently under a run that never happened. An identifier the command minted for itself never warns, because nothing was mistyped.

## Retired Concepts

Ideas from the previous pipeline that do not exist in this one.

- **Greenlit domains** — the skip that skipped resolution for trusted domains. Replaced by ATS collectors arriving already resolved and parsed.
- **Parser confidence scoring** — `parsers/confidence.ts`. Replaced by one source priority list that ranks every parser and collector together, which is the only thing deciding which of two copies of a field survives.
- **Company blacklist** — dropped.
- **`BlockedJob` and `ScrapingRun`** — both tables were empty; `BlockedJob` was written only by the pre-rebuild scraper path.
- **Rejection memory** — dedupe matching a re-collected job against its existing row is sufficient.
- **Deciding where a job is by comparing names** — the old rule compared a job's location text to the user's, which put a job in Austin, Arkansas into the backlog and would match any place called St. Johns against the user's own neighbourhood. A place's own outline on a map decides containment now.
- **A place-type allow and block list** — fifteen rules deciding which kinds of place could ever match. Dropped: the rules are not trusted to be accurate, and the problem they guarded against has not appeared.
- **Throwing a location fragment away before looking it up** — the old prefilter dropped a country as too broad and deleted work-mode words. Every piece is kept now, including one naming nothing on a map, because a real place standing beside junk still has to be judged.
- **A company row holding its own hiring system and slug** — one pair of columns forced two different facts to travel together: that a company posts on a hiring system, and that we poll its board every run. Board rows split them, and a company can have more than one board, which the pair of columns could not express. The list an ATS collector polls is therefore a query over board rows carrying that collector's name, rather than over companies carrying a platform name.
- **One ranking number stored on a job** — the old `calculateScore` multiplied weighted company scores by an age modifier and a salary modifier. The judgements are stored now and the ranking is left to whatever reads them, because a number computed from a formula goes stale the moment the formula changes.
- **A company name built from a board slug** — an invented value cannot be told apart from a real one and will not match the real one. Measured across the 21 seeded slugs, two build a name that can never match the employer: `bjakcareer` against the collected `Bjak`, and `gohighlevel` against the collected `HighLevel`. A company now carries a name, a slug, or both, and never neither.
- **A written note hung on the employer's name** — the old dashboard showed one there. The new database holds no such column: what an agent wrote about an employer is four pieces of reasoning, one per scored category, and the written reasoning on the page now hangs off the total instead.
- **A dashboard that changes anything** — the old page could move a job's status. This one is read-only and writes nothing, not even a record that it was read. Changing a status from the page is a backlog item, to be built over the same code a command-line change runs, so the page and the pipeline cannot disagree about what a status change means.
